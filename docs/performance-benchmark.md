# Performance benchmark

Real, measured latency for the core write/read paths a new user's
first-time flow exercises — signup through creating a knowledge base
and running a keyword search. Generated by
[`apps/api/scripts/benchmark_api.py`](../apps/api/scripts/benchmark_api.py)
(`make api-benchmark`) against a genuinely running server over real
HTTP, the same "run it for real" discipline this project uses
throughout — not `TestClient`'s in-process shortcut.

## What this is, and isn't

These are **local dev machine numbers**, not a production capacity
claim — a single Windows dev box running the full stack (Postgres,
Redis, MinIO, ClamAV) via Docker Compose alongside everything else on
that machine, not dedicated production hardware. There is no honest
"must be under N ms" threshold to assert without a real production-like
benchmark environment, so this script reports numbers, it doesn't grade
them — the same reasoning [`voice/benchmark.py`](../apps/api/voice/benchmark.py)
already established for voice latency.

**Not covered:** document upload/extraction/embedding and dense/hybrid
vector search — both need a real `OPENAI_API_KEY`, which this
environment doesn't have. The same honest gap `voice/benchmark.py` and
`eval/regression.py` already document for the identical reason; a
fake/missing key would produce either an outright failure or a
meaningless number, not a real measurement.

## Results (2026-08-17, local dev)

| Endpoint | Success | Mean | p50 | p95 |
| --- | --- | --- | --- | --- |
| `GET /health` | 20/20 | 15.6ms | 2.2ms | 269.7ms |
| `GET /ready` (real Postgres + Redis round trip) | 20/20 | 23.0ms | 28.2ms | 32.1ms |
| `POST /auth/signup` (real password hashing) | 3/3 | 48.9ms | 44.7ms | 60.5ms |
| `POST /auth/login` (real password verify) | 3/3 | 62.5ms | 44.8ms | 101.8ms |
| `POST /organizations` (org + role + membership + security-settings, one transaction) | 3/3 | 21.6ms | 13.9ms | 40.7ms |
| `POST .../workspaces` | 3/3 | 32.6ms | 18.8ms | 62.3ms |
| `POST .../knowledge-bases` | 3/3 | 45.3ms | 19.3ms | 100.2ms |
| `GET /organizations` (RLS-filtered list) | 20/20 | 7.2ms | 6.2ms | 19.4ms |
| `POST .../search/keyword` (empty KB) | 20/20 | 19.9ms | 16.7ms | 65.8ms |

`GET /health`'s own 269.7ms p95 against a ~2ms median is one slow
outlier in 20 runs (likely a one-off scheduling/GC pause on a shared
dev machine, not a real endpoint cost) — worth another look if it
reproduces consistently in a future run, not treated as a real finding
from a single sample.

Write-path endpoints only ran 3 iterations each, not 20: `POST
/auth/signup` is real-rate-limited to 5/hour per IP
(`routers/auth.py`'s own `rate_limit(key_prefix="signup", limit=5,
window_seconds=3600)`), discovered live while first running this
benchmark (see the script's own `WRITE_ITERATIONS` comment) — a real,
deliberate anti-abuse control, not a benchmark bug, but it does mean
this script can't be rerun with a large write sample more than once per
hour per machine.

## Running it yourself

```bash
make api-dev              # in one terminal
make api-benchmark        # in another
```
